# Mission Log: Pivoting to 9p (and Getting the First Real Boot)

---

## What We Did

The previous session ended with the vsock handshake and OCI pull landed but
two things unproven: no real VM boot had ever happened (virtiofsd was absent
and installing it was off-limits), and the rootfs-share code path had never
executed. The user's call: drop virtiofs for now, go all-in on 9p (QEMU's
in-process `-fsdev local`, no daemon), and re-add virtiofs later in the
performance phase -- explicitly **keeping the virtiofs work recoverable via
git revert**.

### Phase 1: Host switch (`src/main.c`, commit `0a8a186`)

- Removed `start_virtiofsd()`/`stop_virtiofsd()`, the socket dir logic, and
  the virtiofsd pid tracking.
- Replaced the QEMU args: `-chardev socket` + `vhost-user-fs-pci` became
  `-fsdev local,id=fsdev0,path=<rootfs>,security_model=none` +
  `virtio-9p-pci,fsdev=fsdev0,mount_tag=rootfs`.
- Dropped the memfd-shared memory backend (`-object memory-backend-memfd`,
  `-numa node,memdev=mem`) -- it exists only because vhost-user-fs needs
  shared memory; 9p does not.
- Added `panic=-1` to the kernel cmdline. Without it the kernel hangs
  forever after PID1's exec'd process exits (panic on "Attempted to kill
  init"), so QEMU never terminates and no automated test can assert
  completion. `panic=-1` + `-no-reboot` turns entrypoint exit into a clean
  QEMU exit. This was a latent bug for *any* non-interactive run, 9p or not.

### Phase 2: Guest 9p-only + module loading (`guest/init.c`, commit `a9ecd0b`)

- `mount_rootfs()` now mounts 9p only; the virtiofs attempt removed (revert
  restores it).
- Added `load_9p_modules()` (later renamed `load_guest_modules()`): a
  `finit_module()` loop over a fixed dependency-ordered list from
  `/modules` in the initramfs. Needed because a KVM guest is a *separate
  kernel instance*: the host's loaded 9p modules don't count, and module
  autoload can't work (no modprobe in the initramfs). The synthetic kernel
  (ADR-007) builds everything in and ships no `/modules`; the loader is a
  no-op there.
- `guest/build-initramfs.sh` bundles decompressed (`xz -dc`) copies of the
  needed modules from `/lib/modules/$(uname -r)`.

### Phase 3: Kernel config + tests (`kernel/config`, commit `2fb2af7`)

- `CONFIG_VIRTIO_FS=y` removed; added `CONFIG_NET=y`, `CONFIG_NET_9P=y`,
  `CONFIG_NET_9P_VIRTIO=y`, `CONFIG_9P_FS=y`. **`CONFIG_NET_9P` depends on
  `CONFIG_NET`** -- the synthetic kernel's "no guest networking" property
  is temporarily relaxed (documented in ADR-022; restorable when virtiofs
  returns).
- `tests/test_kernel_config.c` required-list and `tests/run_tests.sh`
  checks updated in the same commit to keep every commit green.

### Phase 4: The first real boot (commits `d0d0f5b`, `e478aec`)

Wrote `tests/e2e_boot.sh`: build guest + initramfs, compile a static
`/bin/hello` into a tiny rootfs, run `podvm -r <initramfs> <rootfs>
/bin/hello`, require podvm to exit on its own and `E2E-ROOTFS-OK` on the
serial console. Three failures, three fixes, all on the first boot attempt:

1. **`Property 'virtio-9p-pci.tag' not found`** -- the device property is
   `mount_tag` for virtio-9p-pci (`tag` is the vhost-user-fs spelling).
   QEMU refused to start entirely.
2. **`9pnet: Unknown symbol netfs_write_subrequest_terminated`** -- on
   kernels >= ~6.6, 9pnet links against the `netfs` module. Added
   `netfs.ko` to the bundle and load order (fscache is built into the host
   kernel, so it needs no bundling).
3. **`mount rootfs failed: Invalid argument`** -- the real one. Since the
   fs_context conversion (5.14+), the 9p tag is the mount **source**
   argument; `tag=rootfs` as a data option is rejected with EINVAL. The
   original virtiofs-first code never reached the 9p branch, so this latent
   bug had never fired. Fix: `mount("rootfs", cfg->root, "9p", 0,
   "trans=virtio,version=9p2000.L")`.

After fix 3: **`E2E-ROOTFS-OK`** -- boot, module load, 9p mount, chroot,
exec, clean exit. First real VM boot in the project's history.

### Phase 5: vsock goes live too

Same boot attempt showed `vsock connect to cid 3 failed: No such device`:
the host kernel also builds vsock transports as modules, so the guest had
no virtio-vsock driver. Bundled `vsock.ko`,
`vmw_vsock_virtio_transport_common.ko`, `vmw_vsock_virtio_transport.ko`
(commit `d0d0f5b`). Next boot logged both sides of the handshake:

```
podvm: config sent to guest over vsock
podvm-init: received config from host over vsock
```

This closes the previous session's top unknown ("the handshake itself is
unproven against a running QEMU").

### Phase 6: Docs and commits

- `tests/e2e_boot.sh` wired into `run_tests.sh` (skipped, not WARNed, on
  KVM-less hosts). Suite: **17 PASS / 1 WARN (musl-gcc genuinely absent) /
  0 FAIL**.
- **ADR-022** written: 9p rootfs transport, temporary; includes the exact
  virtiofs restoration checklist and the revert range.
- **ADR-019** status amended to "superseded for now"; stays the design of
  record for virtiofs's return.
- README: diagram, requirements (virtiofsd removed, 9p modules added),

## What We Learned

### Technical

- **The 9p tag is the mount source, not a `tag=` option** (fs_context
  conversion, 5.14+). Passing it in the data string yields EINVAL with no
  kernel log line -- the failure is silent and looks like a transport
  problem, not a syntax one.
- **QEMU 9p device property is `mount_tag`;** `tag` belongs to
  `vhost-user-fs-pci`. Getting it wrong makes QEMU refuse to start at all.
- **9pnet depends on the `netfs` module** on kernels >= ~6.6 (and fscache
  may also be modular elsewhere). Module bundling must be transitive, not
  just "the driver you named". `modules.dep` on the host is the source of
  truth.
- **Guest vsock needs guest-side modules too.** The previous session proved
  the *host* had vhost_vsock; nobody checked whether a fresh kernel instance
  (the guest) had a virtio-vsock driver. Any host-side capability check
  says nothing about the guest.
- **A VM with no fs share cannot boot a useful guest,** and `panic=-1` is
  required for any non-interactive lifecycle. Both were invisible while
  nothing could boot at all.
- **`security_model=none`** works unprivileged for same-uid serving; the
  security-model question is parked in ADR-022 for the virtiofs phase.

### Process

- **The pivot paid for itself on the first boot.** Three real bugs found in
  one sitting, all in code that had sat "done" for weeks behind an
  untestable transport. An e2e boot test is now the project's highest-value
  artifact.
- **Committing each fix as it was found** (mount_tag, netfs, mount source,
  vsock modules) kept the history a readable debugging narrative instead of
  one opaque "make boot work" commit.
- **Revert-range discipline.** Writing the restore instructions into the
  ADR *at pivot time* (while the reason for each removal is fresh) is
  cheaper and more reliable than reconstructing them later.

---

## What We Decided

- **9p is the sole rootfs transport until the functional baseline is
  green** (ADR-022). virtiofs returns as the default in the performance
  phase; 9p's fate then: deleted, or kept as `--fs=` fallback (ADR-021's
  FreeBSD guests need p9fs regardless, which argues for keeping it).
- **virtiofs work is preserved, not discarded.** The whole pivot is a
  revertible commit range: `git revert 0a8a186..e478aec` restores
  virtiofs + virtiofsd + VIRTIO_FS config + test expectations. Nothing was
  history-rewritten.
- **Module bundling is a host-kernel-boot bridge,** not a design. The
  synthetic kernel builds everything in; when it exists, `/modules` and
  `load_guest_modules()` become dead weight to delete.
- **`panic=-1` stays** regardless of transport -- it is a lifecycle
  requirement, not a 9p accommodation.

---

## Rules Added

- **e2e before architecture:** no filesystem-transport or lifecycle claim
  is "done" without `tests/e2e_boot.sh`-style proof against a real boot.
- **Module bundling is transitive:** when shipping `.ko` files into an
  initramfs, resolve the full dependency closure from `modules.dep`, don't
  hand-pick.
- **Guest capability != host capability:** anything checked via
  `/dev/*` or module presence on the host must be re-verified inside the
  guest kernel instance.
- **Revertible pivots get written restore instructions up front:** the ADR
  that justifies a temporary change carries the exact revert range and
  checklist.

---

## What We'd Do Differently

- **The 9p mount branch should have been the tested path from day one.**
  It sat as a "fallback" behind virtiofs in code that never ran, so it
  accumulated two latent bugs (mount option syntax, missing modules)
  undetected. A fallback that has never executed is not a fallback.
- **`load_guest_modules()` uses a hardcoded list** instead of parsing
  `modules.dep`. Fine for four+three modules on one kernel; brittle if the
  host kernel changes its dependency graph. If the synthetic kernel slips,
  parse `modules.dep` (on the host, at initramfs build time).
- **The e2e test asserts vsock only by log grep.** It should eventually
  assert the guest *used* the vsock-provided config (e.g. an env var
  echoed by the entrypoint), not merely that the handshake printed.
